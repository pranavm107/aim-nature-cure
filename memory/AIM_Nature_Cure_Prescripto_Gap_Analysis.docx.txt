1. Purpose of This Document
The PRD (AIM_Nature_Cure_ERP_PRD_v1_0) defines what the system must do. This document answers the next question: given Prescripto — the MERN-stack hospital-management repo you're using as the starting codebase — as-is, what already matches the PRD, what needs rebranding or rework, and what has to be built from zero. It is organized to be read alongside the PRD, section by section, and ends with a revised, Prescripto-specific phase plan and an immediate action list.
2. Bottom-Line Verdict
Prescripto gives you a working three-workspace skeleton (Patient / Admin / Doctor) on the React + Express + MongoDB + JWT stack the PRD already leans toward. That skeleton — auth, role-based routing, a doctor record, and a dashboard shell — is worth keeping and is realistically 10–15% of the total AIM Nature Cure build.
Everything that makes this an ERP for a nature-cure hospital — therapies, packages, consultations, billing beyond a single appointment fee, doctor revenue and incentives, follow-ups, leads, social media proof, personal workspace, daily/weekly/monthly reporting, and audit logs — does not exist in Prescripto today. That is the bulk of the PRD (Sections 5.5 through 5.19) and it is net-new engineering, not adaptation.
One structural point matters more than any single feature: Prescripto's biggest workspace, the patient-facing frontend/ app (booking, patient login, patient profile), maps to a PRD role that is explicitly out of Version 1. Per PRD Section 4.1, only Admin and Doctor are V1 users — patients do not log into the system in Version 1. So frontend/ is not part of the MVP; it's a head start on the "Patient Portal" item the PRD lists under Section 7.3 Future Enhancements. Don't spend Phase 1–9 effort rebranding it — park it.
3. What to KEEP As-Is
Technology stack decision: React (Vite) + Express + MongoDB + JWT auth. This matches PRD Section 12's "likely direction" and removes the need for a stack debate.
Three-workspace repo structure (separate frontend / admin / backend folders) — mirrors the PRD's Admin vs Doctor separation and can absorb a future Patient Portal without restructuring.
JWT authentication pattern and the .env-based secret handling (MONGODB_URI, JWT_SECRET) — satisfies PRD FR-001 and the Security requirements in Section 11.
Role-gated routing pattern already proven across admin/src/pages/Admin and admin/src/pages/Doctor — this is exactly the RBAC shape PRD FR-002 asks for; it just needs Admin/Doctor permissions data-driven instead of folder-based, per FR-004.
doctorModel.js as the seed for the Doctor entity (name, specialty, fees, availability, credentials already present) — extend, don't replace.

10. Immediate Next Steps
Confirm with the team that the frontend/ patient app is parked, not deleted, and is out of the Version 1 timeline — this changes effort estimates significantly if assumed otherwise.
Design the AIM-specific Mongoose schemas for the 23 missing entities (Section 7) before touching any UI — the PRD's business rules (BR-05, BR-06, BR-07: no hard-coded prices, targets, or follow-up counts) need to be schema-level decisions, not UI decisions.
Decide the RBAC approach: keep folder-based admin/doctor separation (fast, matches current repo) vs. move to a single app with a Role/permission table (matches PRD FR-002/FR-004 more literally, more flexible for the Phase-2 Receptionist/Accounts roles in PRD Section 4.2).
Strip Stripe/Razorpay dependencies and the public booking route from the active branch early, so nobody builds new features against a payment flow that's being removed.
Re-run this gap analysis after Phase 3 (Therapies & Packages) — it's the first genuinely new domain model and a good checkpoint on how closely the rest of the build is tracking the PRD.
